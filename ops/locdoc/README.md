# LocDoc OMS evaluation environment

This directory contains the manifests for a private, synthetic-data OMS environment in the `locdoc` namespace of the `lucas_engineering` cluster. The root Argo CD application manages the `locdoc` application from this directory on `main`, with automated sync and self-healing. Do not enable a public ingress while the application's development contact-login bypass is enabled.

The database uses a local-path PVC. Kubernetes Secret `oms-secrets` is created independently of Git and contains the PostgreSQL password, database URL, and two random signing secrets. Preserve the PVC and Secret together. The initialization Job runs migrations, installs PostgreSQL number triggers, and applies the guarded synthetic seed from the local OMS worktree. It is intended for an empty evaluation database, not a production database.

After initialization and a healthy rollout, an authorized cluster operator can connect locally with `kubectl --context lucas_engineering -n locdoc port-forward service/oms 8080:8080`, open `http://localhost:8080`, and select **Support Account**. Namespace ingress is restricted to pods labeled as part of OMS. The application uses development authentication and synthetic records, and external services are not configured as production integrations.

The application image was built from the local `/home/wardl/Locdoc/oms-cluster` worktree based on OMS upstream commit `f1ec97b0`, with uncommitted local source and seed changes. That source is not in the remote OMS repository, so the image cannot be reproduced from the upstream commit alone; preserve the worktree until a separate source release is authorized. `image-transfer.yaml` and `publish-image.py` document the temporary image-transfer path using the existing TLS-protected registry gateway and Kubernetes-mounted credentials; no credential values are recorded here.

## Mock integrations

`object-store.yaml` runs a namespace-private S3-compatible store on a separate 5 GiB PVC. `object-store-init.yaml` creates the `oms-local` bucket. OMS is configured with `OMS_MOCK_S3=true`, the internal S3 endpoint, and mock credentials; object URLs use the authenticated same-origin `/api/mock-objects/` route, which restricts retrieval to the signed-in provider's prefix. Preserve `oms-objects` along with the database. The `oms-secrets` PostgreSQL password is also used as the local mock store's secret key, so it must not be changed independently of the store.

`mailpit.yaml` captures SMTP mail inside the namespace; its mailbox is ephemeral and messages are lost when the pod is replaced. `seed-mock-email.sql` only accepts the `oms_test` database with the two known synthetic providers. The ConfigMap and Job derived from it apply the seed idempotently. To inspect the mailbox locally, run `kubectl --context lucas_engineering -n locdoc port-forward service/oms-mailpit 8025:8025` and open `http://localhost:8025`. The fixture accounts use non-secret test credentials. No SMTP forwarding or public ingress is configured.

The image includes local source changes in `/home/wardl/Locdoc/oms-cluster`, including the corrected PostgreSQL catch-up migration, generated synthetic fixtures, and the mock object route. `Dockerfile.cluster` builds those changes from the worktree. A fresh database uses the corrected full migration; the `catchup-repair` resources document the one-time repair of the initial failed migration on this database and should not be run on a fresh installation. For a fresh environment, provision the independently managed secret, apply the database and object store, wait for readiness, run initialization, the object-store initialization Job, and the mock email, supplier, and payment seed Jobs, then start OMS. These one-time Jobs and repair resources are deliberately excluded from `kustomization.yaml` so routine Argo syncs cannot rerun them or replace immutable Jobs. The four PVCs have Argo prune and deletion protection; removing the application is not a database backup. Preserve and back up the PVCs and secret together.

`payment-mock.yaml` runs a stateful, private simulated payment service on the `oms-payment-mock` PVC, with `stripe-mock.yaml` supplying schema-only responses for other Stripe API calls. `OMS_MOCK_STRIPE=true` forces a fixed fixture key and private endpoint, and OMS refuses this setting in production. Signed-in staff in the two synthetic providers can simulate work-order checkout; the UI says no money is charged, and payment records are labeled `Simulated`. Public checkout, subscriptions, terminal devices, real Stripe.js confirmation, and settlement are not simulated. Public work-order URLs use reversible encoding and must not be treated as authorization tokens for a new public payment flow. Mock intents and payments must never be treated as real transactions. The mock webhook uses a fixture-only signing secret; real-mode webhooks require a configured signing secret.

`maps-mock.yaml` supplies a fixed, simulated one-mile distance for backend work-order updates. It is enabled only in development or testing with `OMS_MOCK_MAPS=true`; it does not provide live routing or browser maps. `seed-mock-payment.sql` adds synthetic payment examples and is idempotent without resetting completed payments. Work orders 900002, 900003, and 900004 have been used for checkout verification.


`seclock-mock.yaml` and `seclock-mock-config.yaml` provide a synthetic supplier catalog, availability and simulated orders, with SQLite persisted on the `oms-seclock-mock` PVC. `seed-mock-seclock.sql` and its ConfigMap/Job enable the integration for Demo Provider and add a dedicated fake product and purchase order 900001. The seed checks the database, tenant, and fixture IDs and does not reset a previously placed mock order. `OMS_MOCK_SECLOCK=true` routes all OMS Seclock calls to the fixed private service using fixture-only credentials, and OMS refuses mock mode in production. Orders returned with `MOCK-` IDs are simulations and are never sent to a supplier. Orders are isolated by synthetic provider in the mock service. Purchase order 900001 was exercised once and now carries a simulated order ID; re-running the seed deliberately does not erase its state.
