# Scheduled cluster maintenance

The [lucas_engineering cluster maintenance Linear project](https://linear.app/lucas-engineering/project/lucas-engineering-cluster-maintenance-026cce2f7470) is the work board for the `lucas_engineering` k3s cluster. The weekly Sol planner creates and updates issues there. Four Luna workers pick up issues for security, Helm charts, Kubernetes, and general maintenance. This directory retains the standing policy and issue template. The old Markdown tickets are archived locally for reference and are no longer a queue. Keep the computer and ChatGPT desktop app running during scheduled hours.

## Ticket contract

Create each ticket as one issue in the Linear project, using [TEMPLATE.md](TEMPLATE.md) for its description. Use exactly one category label: `maintenance:security`, `maintenance:helm`, `maintenance:kubernetes`, or `maintenance:general`. Linear status and labels are authoritative: `Todo` means queued and actionable, `In Progress` means claimed, `In Progress` plus `maintenance:review` means awaiting review, `Backlog` plus `maintenance:blocked` means blocked, and `Done` means complete. Do not create a duplicate for an unfinished issue; update the existing issue with fresh evidence. The planner creates at most eight new issues per week and at most two per category. Workers take the highest-priority `Todo` issue in their category, one issue per run. Record timestamps in America/New_York. When the planner or worker resolves a blocker or grants approval under the delegation below, append the decision, exact scope and delegation reference; remove the blocker/review label and return it to `Todo` if worker action remains. Preserve earlier approvals and work logs as history. Never rewrite a past rollout as having received a new approval retroactively.

Every issue must identify the exact target and current version, a verified candidate version or maintenance action, sources and release notes, likely impact, validation, rollback, and whether an approval gate applies. If any of these are unknown, the worker may investigate but must not deploy. Never put credentials, Secret values, kubeconfigs, or workload environment data in issues or run output. If Linear is unavailable, report the failed access and stop queue work; do not silently resume the archived file queue.

## Standing change policy

### Human delegation — 2026-11-10

The user confirmed in the weekly planner thread that `lucas_engineering` is a **development cluster**, including namespaces and applications named production, and delegated maintenance approval decisions to Codex: “when the other worker that you create tasks for put things into blocked, you have my permission to unblock them.” This supersedes this directory's former requirement for a separate human approval for every platform or major/minor upgrade. Reference this decision as `user delegation 2026-11-10, weekly planner thread 01a15177-5911-7710-ae19-081695626ea0`.

The planner may review and approve a scoped maintenance action, remove an approval blocker, and queue it for a worker. Workers may also exercise this delegation after reviewing the concrete change and recording the decision in Linear. Permission is no longer a blocker solely because work involves a core component, a major/minor upgrade, Kubernetes/k3s or nodes, CRDs, RBAC, NetworkPolicy, Secret references, ingress, storage, databases, or a data migration. Expected bounded dev-service downtime is accepted. Existing access and credential protections still apply.

Authorized work on the explicit `lucas_engineering` context includes bounded observation and upstream research; isolated source edits and dependency preparation; reviewable PRs; merge, GitOps reconciliation and observation; scoped node maintenance; backups, restored-copy rehearsals and supported migrations; and recoverable rollback. For dependency maintenance outside a PHarness execution, workers may fetch the named source and upstream packages, edit dependency manifests/lockfiles, and prepare an isolated test environment. PHarness run-contract restrictions remain applicable inside actual PHarness jobs; do not silently alter or falsify those contracts.

### Technical gates and execution

Before merge or deployment, use a clean isolated worktree from current remote main, check the live Argo revision and target baseline, keep one scoped target per change, inspect the actual diff/render and upstream compatibility, run relevant tests and configured CI, record exact commits and immutable image/chart versions, and establish validation and rollback appropriate to the change. Review resource identity, CRD compatibility, permissions, networking and persistent data whenever affected. Record the concrete delegated approval and conditions in Linear before execution; it is not a fabricated GitHub human review and does not bypass branch protection.

Workers should obtain missing evidence, prepare backups or isolated rehearsals, install required test tools in isolated environments, and fix scoped validation failures when these are achievable within the ticket. Queue that concrete next step rather than treating an unfinished preflight or a missing generic human approval as an external blocker. Missing evidence is not a passing check: do not deploy until relevant gates pass. Stop further deployments on failed target checks, unresolved drift, uncertain ownership, inaccessible required credentials, or an unhealthy baseline, and record the exact remaining blocker. An unrelated operator-doctor failure does not prove the target is unhealthy.

For stateful changes, preserve the existing data, verify a usable backup/restore or supported migration/recovery path, and test compatibility before switching the live service. For node work, verify installation flags, datastore recovery and workload placement, then proceed one node at a time. For self-managed Argo CD, retain a recovery route independent of the changed component. Authorized temporary validation resources may be cleaned up by their exact recorded identities; this delegation does not authorize irreversible deletion of existing user data/PVCs, wiping a cluster, exposing credentials, or work outside the named dev environment. Those actions require specific user direction.

Approval from issue existence, priority, elapsed time or a historical planning approval must still never be inferred. Use the November 10 delegation explicitly. A new scoped decision supersedes historical approval-only blockers while preserving their original text. Already deployed changes should be validated and closed without repeating the rollout.

Follow [the GitOps workflow](../../docs/gitops-workflow.md), [the permissions model](../../docs/permissions-model.md), and [the maintained cluster operator interface](../../docs/operations/ASTRA-CLUSTER-DEVELOPMENT.md), with this later user delegation controlling maintenance approval decisions where older guidance differs. Use the explicit `lucas_engineering` context and profile-selected kubeconfig for every cluster operation. Never switch the current context or directly override an Argo-owned resource. The weekly planner remains an observer, reviewer and queue manager; scheduled workers execute scoped changes. A failed deployment stops further deployments for that run and is reported with evidence; do not improvise a destructive recovery.

## Run order

The planner runs Sunday at 8 PM. Workers run Monday through Friday at 1 AM (`security`), 2 AM (`helm`), 3 AM (`kubernetes`), and 4 AM (`general`), America/New_York. Workers do nothing and stay quiet when their category has no actionable Linear issue. The planner reviews unfinished issues before adding new ones, and prioritizes supported security fixes and existing unhealthy conditions over novelty.
